# テストと手動確認の手順

## 自動テスト

| コマンド         | 内容                                                                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm test`      | Vitest。core（NUT-00/12 テストベクター含む）、server（API・プライバシー・削除ジョブ・マイグレーション）、web（IndexedDB・オフライン受付・辞書） |
| `pnpm e2e`       | Playwright。作成→取得→入場→再入場拒否、バックアップ復元、有料→返却、招待リンク、オフライン受付2台→競合、言語切替                                |
| `pnpm lint`      | ESLint と Prettier                                                                                                                              |
| `pnpm typecheck` | TypeScript                                                                                                                                      |

### NWC（有料チケット）のモック

自動テストは実ウォレットに接続しません。

- **単体テスト**（`apps/server/test/phase2.test.ts`）：`MockWalletBackend` を注入し、請求書の作成、
  `lookup_invoice` による支払い確認、入金通知、ウォレットの障害、権限不足の接続を確かめます。
- **E2E**：サーバーを `KAMEN_MOCK_WALLET=1` で起動します（`playwright.config.ts`）。請求書は作成の
  1.5秒後に支払い済みになります。接続文字列は形式だけ確認されます。
  `NODE_ENV=production` では起動を拒否します。

ローカルで画面を試すときも同じモックを使えます。

```bash
cd apps/server && KAMEN_MASTER_KEY=$(openssl rand -hex 32) KAMEN_MOCK_WALLET=1 KAMEN_MOCK_WALLET_SETTLE_MS=10000 pnpm dev
```

## 実ウォレットでの手動確認（有料チケット）

実際の Lightning ウォレットで、請求書の作成から入場までを確かめる手順です。少額（数 sats）で行ってください。

### 準備

1. NWC に対応したウォレットを用意します（例：Alby Hub、coinos）。
2. ウォレットで新しい接続（App Connection）を作ります。権限は **請求書の作成（make_invoice）と
   確認（lookup_invoice）だけ** にします。支払い権限（pay_invoice など）は付けません。
   入金通知（notifications）が選べる場合は有効にします。
3. 接続文字列（`nostr+walletconnect://...`）を控えます。
4. 支払う側として、別の Lightning ウォレットを用意します。
5. サーバーを **モックなし** で起動します（`KAMEN_MOCK_WALLET` を設定しない）。サーバーから NWC の
   リレー（接続文字列の `relay=`）へ WebSocket で接続できる必要があります。

### 手順と期待する結果

| #   | 操作                                                                           | 期待する結果                                                                                   |
| --- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 1   | 主催者として、発行条件「有料」、価格 5 sats のイベントを作成する               | 管理画面に「ウォレット（NWC）」カードが出て、「未接続」と表示される                            |
| 2   | 接続文字列を貼り付けて「接続」                                                 | 「接続済み」になる。支払い権限のある接続を使った場合は警告が出る                               |
| 3   | 支払い権限のない接続で、`make_invoice` を外した接続を試す（任意）              | 「この接続では請求書を作成・確認できません」と表示され、保存されない                           |
| 4   | 公開して、別のブラウザ（スマホ）でイベントページを開く                         | 「5 sats で参加する」ボタンが出る                                                              |
| 5   | ボタンを押す                                                                   | 請求書の QR が出る。主催者のウォレットにも同じ請求書（未払い）が見える                         |
| 6   | 支払う側のウォレットで QR を読み取って支払う                                   | 数秒以内に「支払いを確認しました」→ チケット画面に切り替わる。主催者のウォレットに 5 sats 入る |
| 7   | 手順5のあと、支払う前にタブを閉じ、支払ってからイベントページを開き直す        | 支払い待ちの続きから再開し、チケットを受け取れる                                               |
| 8   | 請求書を出したまま15分待つ                                                     | 「請求書の期限が切れました」と表示され、新しい請求書を作れる                                   |
| 9   | 受付リンクでチケットを読み取る                                                 | 入場OK。同じ QR をもう一度読むと「使用済みです」                                               |
| 10  | 主催者の管理画面を見る                                                         | 発行1・来場1。参加者の名前やウォレットの情報はどこにも表示されない                             |
| 11  | サーバーの DB を確認する（`sqlite3 data/kamen.sqlite 'select * from quotes'`） | payment_hash、状態、期限だけが入っている。請求書の文字列や支払った人の情報はない               |
| 12  | ウォレットの接続を解除する                                                     | 「未接続」に戻り、新しい購入はできなくなる                                                     |

確認できたら、使ったウォレットのアプリ一覧からこの接続を削除してください。

## オフライン受付の手動確認（機内モード）

1. 主催者として「オフライン受付を使う」にチェックしてイベントを作り、公開する。
2. 参加者のスマホでチケットを取る。チケット画面に「オフライン受付のため…」の注意が出ることを確認する。
3. 受付スタッフのスマホで受付リンクを開く（**この時点ではオンライン**。公開鍵と使用済みリストが端末に保存される）。
   ホーム画面に追加しておくと、オフラインでも開き直せる。
4. 受付スタッフのスマホを機内モードにする。オレンジの警告「オフライン：端末内の記録で判定しています…」が常に出ることを確認する。
5. チケットの QR を読む → 「入場OK（オフライン判定）」、「未同期 1 件」と出る。
6. 同じ QR をもう一度読む → 「この端末で使用済みです」。
7. 受付端末を2台用意し、両方を機内モードにして同じ QR を読む → 2台とも入場OKになる（既知の限界）。
8. 1台ずつ機内モードを解除する → 先に戻った端末は「未同期」が消え、後から戻った端末には「競合」の一覧が出る。
9. 機内モードのまま、オフライン受付を使わないイベントの受付リンクで読む →
   「このイベントはオフライン受付に対応していません」と出る。

## ルーム（Marmot）の手動確認

1. テスト用リレーを起動する（または `docker compose --profile devrelay up -d` で ws://localhost:7777）。

   ```bash
   pnpm --filter @kamen/messaging relay
   ```

2. 同じ `KAMEN_MASTER_KEY` と `ROOM_RELAYS=ws://127.0.0.1:7777` で、ルームエージェントと API サーバーを起動する。

   ```bash
   cd apps/server && KAMEN_MASTER_KEY=... ROOM_RELAYS=ws://127.0.0.1:7777 pnpm agent
   ```

   ```bash
   cd apps/server && KAMEN_MASTER_KEY=... ROOM_RELAYS=ws://127.0.0.1:7777 pnpm dev
   ```

3. Web を `KAMEN_CSP_CONNECT=ws://127.0.0.1:7777` 付きの `vite preview`（または `pnpm --filter @kamen/web dev`）で開く。
4. 主催者としてイベントを作り公開する（「ルームを使う」が既定でオン）。
5. スマホ3台（または別ブラウザ3つ）でチケットを取り、チケット画面の「ルームに入る」から入室する。仮面と名前が3人とも違うこと、プライバシーの注意（エージェントは読める、リレーに IP が見える）が表示されることを確認する。
6. 会話が全員に届くこと、主催者のお知らせがルームで強調表示されることを確認する。
7. 主催者の管理画面で「ルームを今すぐ解散」→ 全員に「このルームは解散しました」と出て、ルームの履歴が消えることを確認する。
8. エージェントを止めた状態で、チケット取得と入場が普段どおりできること、「ルームに入る」が失敗しても入室パスが残っていることを確認する。
