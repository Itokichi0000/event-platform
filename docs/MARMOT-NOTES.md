## 仕様の現状（SPEC 5章からの変化）

- **MIP は廃止された。** 仕様は「Marmot v2」として、面（surface）ごとの文書に再編されている（`foundation/`、`protocol-core/`、`app-components/`、`transports/`、`features/`）。MIP-00〜03 の内容はこれらに移り、`mip-coverage.md` に対応表がある。
- 仕様は日単位で変わっている（`changes.md` に11月だけで20件以上。多くは複数端末まわり）。バージョン番号はない。
- 参照実装は Rust の MDK（White Noise が使用）。marmot-ts は「darkmatter 参照実装とワイヤ互換」をうたい、MDK v0.13〜0.14-dev との相互運用テストの記録がある（`docs/guide/mdk-compatibility.md`）。
- SPEC 10章にある2026年3月の破壊的変更（NIP-44 → ChaCha20-Poly1305）は、現行仕様では kind 445 の外側の暗号化（MLS エクスポーター由来の鍵）として反映済み。Welcome のギフトラップは引き続き NIP-59（NIP-44）。

## Nostr 上に出るもの（リレー運営者に見えるもの）

| kind                         | 中身                              | リレーに見えるメタデータ                                                                                         |
| ---------------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 445 グループメッセージ       | MLS メッセージを外側でも暗号化    | **イベントごとに新しい使い捨て公開鍵**で署名。タグは `h`（グループのルーティング ID）だけ（任意で `expiration`） |
| 1059 ギフトラップ（Welcome） | kind 13 シール → kind 444 Welcome | `p` タグ＝受信者の公開鍵（参加者の使い捨て鍵）。送信者はシールの中で、リレーには見えない                         |
| 30443 鍵パッケージ           | 公開の鍵パッケージ                | 作成者の公開鍵、`d` タグ（スロット）                                                                             |
| 10002 / 10050                | リレーリスト                      | 通常のアカウントはこれで鍵パッケージと Welcome の宛先を公開する                                                  |

**この実装での最小化**：`getUserInboxRelays` は我々のアダプターが答えるので、参加者はリレーリスト（10002 / 10050）を公開しなくてよい。鍵パッケージ（30443）もアダプターで捕まえてルームエージェントへ HTTP で直接渡せば、リレーに出さずに済む（Welcome の `e` タグはイベント ID を指すだけで、受信者本人は自分の鍵パッケージを持っている）。結果としてリレーに出るのは kind 445 と、参加者宛ての kind 1059 だけになる。

## Node.js での試作（scratchpad、プロジェクトには入れていない）

偽のリレー（メモリ上）、ルームエージェント1、使い捨て鍵の参加者3人で、Node 22 上で試した。

| 手順                                                                                 | 結果                                                                                        |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| エージェントがグループ作成（自分だけ管理者）                                         | 92ms                                                                                        |
| 参加者が鍵パッケージ作成 → エージェントが1人ずつ招待 → 参加者が Welcome を開いて参加 | 1人あたり約80〜120ms。3人で epoch 3                                                         |
| 全員が kind 445 を取り込んで同期                                                     | 全員 epoch 3 で一致                                                                         |
| 参加者 A の発言、エージェントのお知らせ                                              | 他の全員が受信。送信は合意形成の待ち（既定 `settlement_quiescence_ms = 1000`）で約1秒かかる |
| kind 445 の外形                                                                      | 5件すべて別の公開鍵、タグは `h` のみ                                                        |
| メンバー C の削除                                                                    | C は `removed`                                                                              |
| `group.disband()`                                                                    | `acknowledged`。約1.2秒後に全員 `disbanded`                                                 |

**結論**：marmot-ts は Node.js で安定して動く。SPEC 10章の代替案（MDK ベースの marmot-server を Docker で使う）は今回は不要。

## ブラウザでの見込み

- esbuild でブラウザ向けにまとめると、minify 後で約716KB、gzip 後で約221KB。Node 専用モジュールには依存していない。ルーム画面だけを遅延読み込みにすれば、チケット取得の速さには影響しない。
- 保存先は、参加者のチケットとは別の IndexedDB データベースに `GenericKeyValueStore` を実装する。

## 既知の制限・リスク

1. **アルファ版で、仕様も毎日変わる。** バージョンを 0.9.0 に固定し、呼び出しは `packages/messaging` に閉じ込める。
2. **ルームエージェントはグループのメンバー（管理者）なので、ルームの会話を読める。** MLS では、メンバーを追加できるのは現メンバーの管理者だけで、主催者が常時オンラインでない限り、サーバー側のエージェントが管理者になるしかない。リレー運営者には読めないが、**サーバー運営者は（改造すれば）読める**。チケットのように「サーバーを信頼しなくてよい」性質はない。
3. **合意形成の待ち（約1秒）** があるため、送信やメンバー追加は即時ではない。
4. **参加が集中したとき**：1人ごとに1コミットだと、200人のイベントでは後から入った人ほど多くのコミットを取り込む。数秒ごとに複数人の Add を1コミットにまとめると軽くなる（それでもエージェント内では直列）。
5. **時限消滅は助言的。** NIP-40 の `expiration` を守るかはリレー次第。前方秘匿性があるので、鍵を消した後は復号できない。画面の撮影は防げない（SPEC 5章のとおり）。
6. **White Noise との相互運用**：MDK との互換テストは marmot-ts 側で行われているが、こちらでは実機がないため試していない。フェーズ3の完了条件には含めない。

## 実装方針（案）

承認後に、SPEC の該当箇所と PRIVACY.md を同じ方針で更新してから実装する。

1. **`packages/messaging`**
   - `MessagingAdapter`（createRoom / publishKeyPackage / addMember / join / send / subscribe / leave / destroy）を定義する。
   - marmot-ts 実装（`MarmotAdapter`）と、テスト用のメモリ実装（`InMemoryAdapter`）を作る。
   - nostr-tools の SimplePool によるネットワークアダプターを作る。このアダプターは、鍵パッケージをリレーに出さずに捕まえ、受信リレーには設定したルームのリレーを返す。
   - アプリ側は marmot-ts を import しない（ESLint の `no-restricted-imports` で強制する）。
2. **入室パス**
   - `issue` で ticket と room を同時に発行する（outputs に `room` を追加）。
   - room 鍵セットは新規イベントの作成時に作る。既存イベントでは、ルームを有効にしたときに作る。
3. **`POST /api/events/:id/room/join`**
   - 入室パス（DLEQ なし）と、使い捨て鍵で署名した鍵パッケージイベントを受け取る。
   - パスを検証して消し込み、エージェントに追加を依頼する。失敗したら消し込みを取り消す。
   - Welcome のギフトラップはリレーに出すのに加えて、HTTP の応答でも返す（リレーの取りこぼし対策）。
4. **ルームエージェント（`apps/server/src/agent/`、別プロセス）**
   - API サーバーとは内部 HTTP（共有シークレット、Docker 内ネットワークのみ）でつなぐ。
   - イベントごとに専用の Nostr 鍵を、マスター鍵から HKDF で導く。こうすると、イベントをまたいでエージェントの公開鍵からルームを結びつけられない。
   - MLS の状態はマスター鍵で暗号化して別の SQLite に保存する。
   - メンバー追加は直列キューで処理し、数秒ごとにまとめて1コミットにする。
   - お知らせをルームにも投稿する。終了24時間後に解散し、状態を削除する。
   - 会話は保存もログ出力もしない。
5. **Web**
   - イベントごとに使い捨ての Nostr 鍵を作り、IndexedDB（ルーム専用の DB）に保存する。
   - ルーム画面を作る。仮面アバターとランダムな名前は公開鍵から決定的に生成し（SVG と単語リストを同梱）、エージェントの投稿は「主催者のお知らせ」として強調する。
   - 解散を検知したら、端末内の履歴と鍵を削除する。ルーム画面は遅延読み込みにする。
6. **リレーの設定**
   - 環境変数 `ROOM_RELAYS` で指定する。未設定ならルーム機能は無効にし、チケットと入場は従来どおり動く。
   - 既定値は複数の公開リレーにする（候補は承認時に決める）。
   - docker-compose に開発・テスト用のローカルリレーを追加する。E2E 用にはテストコード内に最小の NIP-01 リレーを置く。
7. **テスト**
   - messaging はメモリ実装と marmot-ts 実装（ローカルリレー）で同じテストを通す。
   - E2E はブラウザ3つで、入室 → 会話 → 解散。
   - エージェントやリレーが落ちていても、チケット取得と入場が動くことを確認する。
