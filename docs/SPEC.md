2026年11月15日

---

## 1. 概要と設計原則

身元を明かさずに物理イベントへ参加登録・入場できる、ビットコイナー向けのオープンソースWebアプリを作る。仮称は「Kamen」。アプリストアを通さず、ブラウザだけで動くPWAとして提供する。

### 対象

- **参加者**：アカウント・名前・参加履歴を結びつけられたくないビットコイナー
- **主催者**：小〜中規模（〜200人）のビットコイン系ミートアップの運営者

### 譲らない原則

1. **集めないものは漏れない。** メール・氏名・電話番号の入力欄を作らない。任意項目としても置かない。
2. **発行と入場を紐づけない。** チケットはブラインド署名で発行し、サーバーも主催者も「誰に発行したチケットが使われたか」を知り得ない構造にする。
3. **主催者に必要なのは「正当な1人か」だけ。** 人数、二重入場の防止、連絡手段、ドタキャン対策を、身元なしで満たす。
4. **資金を預からない。** 支払いは主催者自身のLightningウォレットへ直接届く。プラットフォームは残高を持たない。
5. **検証できる。** 全コードを公開し、Docker一発でセルフホストできる。サーバーが何を保存するかをドキュメントとコードで示す。
6. **開示は参加者が選ぶ。** 既定は「何も出さない」。ニックネームやnpubは、参加者がイベントごとに自分で出す。

### やらないこと（初期）

- 法定通貨決済、領収書発行、本名名簿が必須の会場への対応
- ソーシャルグラフを使ったイベント発見（参加履歴の公開と表裏一体のため）
- ネイティブアプリ

## 2. 匿名性と運営利便性のバランス

主催者の要望を7つに分解し、それぞれを身元なしで満たす。満たせないものは「主催者がイベントごとに選ぶ設定」として明示し、匿名性がどこまで下がるかを参加者に表示する。

| 主催者の要望 | 解決策 | 匿名性への影響 |
| --- | --- | --- |
| 申込数・来場数を知りたい | 発行枚数と消込枚数のカウンターをダッシュボードに表示 | なし |
| 二重入場・偽造を防ぎたい | ブラインド署名チケットを受付で消し込む（使用済みリストと照合） | なし |
| 参加者に連絡したい（変更・中止） | イベントごとのMarmot暗号化グループに投稿。参加者は使い捨て鍵で入る | なし（使い捨て鍵のため） |
| ドタキャンを減らしたい | Lightningのhold invoiceによるデポジット（後述、制約あり） | 小：受付時に支払いと来場が紐づく |
| 無料枠の買い占めを防ぎたい | 招待コード、少額の登録料、計算量証明（PoW）から主催者が選ぶ | なし〜小 |
| 参加者を選びたい（承認制） | npubで申請 → 承認後にブラインド発行 | 中：主催者は承認者の一覧を知る。誰が実際に来たかは紐づかない |
| 共同主催・受付スタッフを置きたい | 共同主催者はnpubで追加、受付は権限付きリンクで共有 | なし |

### 主催者が得られないもの

以下は意図的に提供しない。主催者向けの説明にも明記する。

- 参加者名簿のエクスポート（存在しないため）
- イベントをまたいだ「常連」の特定（参加者がスタンプを自分から見せた場合を除く）
- 個別チケットの遠隔取り消し（誰のチケットか分からないため。イベント全体の中止は可能）

### 脅威モデル

| 相手 | 守るもの | 手段 |
| --- | --- | --- |
| サーバー運営者・侵入者 | 登録と入場の紐づけ、参加履歴 | ブラインド署名。IPアドレスやアクセスログを保存しない。Cookie・解析タグなし |
| 主催者 | 参加者の身元 | 個人情報の入力欄がない。ルーム内の鍵はイベントごとに使い捨て |
| リレー運営者 | ルームの内容と参加者 | Marmot（MLS）による暗号化 |
| 他の参加者 | npub・本名 | 仮面アバター。npub交換は双方が同意したときだけ |

守れないものも明記する。会場で顔は見られる。参加者が5人のイベントでは匿名集合が5人しかない。TorやVPNを使わなければ、通信経路上の第三者にはIPが見える。

## 3. システム構成と技術スタック

TypeScriptのモノレポ1つで、Webクライアント（PWA）と軽量サーバーを作る。秘密情報（チケット、使い捨て鍵、スタンプ）はすべて参加者のブラウザ内に置き、サーバーは「署名」と「使用済みの記録」だけを担う。

| 部品 | 役割 | 知っていること |
| --- | --- | --- |
| 参加者PWA | 鍵生成、チケットのブラインド化と保管、QR表示、ルーム参加、御朱印帳 | 自分のチケットと鍵（端末内のみ） |
| 主催者ダッシュボード | イベント作成、カウンター、お知らせ投稿、受付リンク発行 | 集計値のみ |
| 受付スキャナー（PWA） | QR読み取り、署名検証、消し込み、オフライン時の一時保管 | 提示されたチケットが有効かどうか |
| APIサーバー | イベント情報の配信、ブラインド署名、使用済みリスト、請求書の作成依頼 | 発行枚数、使用済みの照合値、支払い状態 |
| ルームエージェント | Marmotグループの管理者として常駐し、入室パスと引き換えにメンバーを追加 | 使い捨て公開鍵の一覧 |
| 主催者のLightningウォレット | NWC経由で請求書を作成・確認（資金は主催者に直接入る） | 入金の事実 |
| Nostrリレー | MarmotメッセージとNWC通信の運搬、イベント告知（任意） | 暗号文のみ |

### 採用技術

| 領域 | 採用 | 備考 |
| --- | --- | --- |
| 言語・構成 | TypeScript、pnpmワークスペース | apps/web、apps/server、packages/core、packages/messaging |
| フロント | React + Vite + vite-plugin-pwa | 静的ファイルとして配布でき、セルフホストが簡単 |
| UI | Tailwind CSS + shadcn/ui、lucideアイコン | 無料・オープンソースのUI素材を積極的に使う |
| 端末内保存 | IndexedDB | チケット・鍵・スタンプ。文字列でのバックアップ書き出しを必ず用意 |
| サーバー | Node.js + Hono + SQLite | Docker Composeで起動。アクセスログは既定で無効 |
| チケット暗号 | Cashuのブラインド署名（BDHKE）とDLEQ証明 | cashu-tsの暗号プリミティブ、または@noble/curvesで実装 |
| メッセージング | marmot-ts（@internet-privacy/marmot-ts） | アルファ版。アダプター層で隔離する（5章） |
| 支払い | NWC（NIP-47）、@getalby/sdk | 通常の請求書とhold invoice |
| Nostr | nostr-tools | 主催者ログイン（NIP-07 / NIP-46）、告知（NIP-52、任意） |
| QR | qrcode（生成）、qr-scanner（読み取り） | |
| テスト | Vitest、Playwright | 暗号部分は単体テスト必須 |
| ライセンス | MIT（案） | 改変版のソース公開を義務化したい場合はAGPLv3。公開前に決める |

ライブラリのAPIは変わりやすい。実装時は各リポジトリの最新READMEを読み、バージョンを固定する。

## 4. チケット設計

チケットは「金銭価値のないCashuトークン」として作る。Cashuと同じブラインド署名（BDHKE）を使うが、satsの残高は表さず、「このイベントに1回入場できる」ことだけを表す。サーバーが資金を預からずに済む。

### 鍵セット

| 鍵セット | 単位 | 用途 |
| --- | --- | --- |
| ticket | イベントごと | 入場チケット。1枚＝1人 |
| room | イベントごと | Marmotルームへの入室パス。1枚＝使い捨て鍵1つ |
| stamp | 主催者ごと | 御朱印（参加実績）。イベントを区別しないので、見せてもどの回か分からない |

チケット取得時に ticket と room を1枚ずつ同時に発行する。別々の鍵セットで署名するため、ルーム内の使い捨て鍵と入場の事実は紐づかない。

### 発行と消し込みの仕組み

1. ブラウザが乱数の秘密値 `x` を作り、ブラインド化した値 `B_` だけをサーバーへ送る。
2. サーバーは発行条件（招待コード、PoW、支払い済み）を確認し、`B_` に署名して `C_` とDLEQ証明を返す。発行枚数を1増やす。`B_` は保存しない。
3. ブラウザがブラインドを外して署名 `C` を得る。DLEQを検証し、`{x, C, dleq}` をIndexedDBに保存する。
4. 受付でQR（`{eventId, keysetId, x, C, dleq}`）を提示する。
5. スキャナーがDLEQをイベントの公開鍵で検証する（オフラインでも可能）。
6. サーバーが署名を検証し、`x` の照合値が使用済みリストになければ追加して入場OKを返す。

サーバーが見るのは手順2の `B_` と手順6の `x` だけで、両者を結びつける計算はできない。これが匿名性の根拠になる。

### 運用上の決めごと

- **オフライン受付**：会場の電波が悪い場合、スキャナーはDLEQ検証と端末内の使用済みリストで判定し、復帰後にサーバーへ同期する。受付端末が複数あるときは二重入場を防ぎきれないため、画面に警告を出す。
- **持参人式**：QRを持っている人が入場できる。譲渡はQRを渡すだけ。コピー対策（端末鍵へのロック）は後のフェーズで検討する。
- **紛失対策**：チケットはブラウザ内にしかない。取得直後に「文字列でバックアップ」「画像で保存」を促す。プライベートブラウズでは閉じると消えることを警告する。
- **キャンセル**：参加者がチケットを返却すると使用済みになり、枠が1つ戻る。

### 支払いとデポジット

- **有料チケット**：サーバーが主催者のウォレットにNWCで請求書を作らせ、支払い確認後にブラインド署名を返す。資金は主催者に直接入る。
- **デポジット（後のフェーズ）**：NWCのhold invoice（`make_hold_invoice` / `settle_hold_invoice` / `cancel_hold_invoice`）を使う。来場者は受付で支払いハッシュを提示してキャンセル（返金）を受け、来なかった人の分だけ決済される。
- デポジットには制約が2つある。hold invoiceは長期間保持できないため、受付開始を開催の数日前に限る必要がある（保持可能な期間は要検証）。また、受付で支払いと来場が紐づく。参加者にはこの点を申込画面で表示する。

### 御朱印（スタンプ）

チェックイン時に、QRへ含めたブラインド値に対して stamp 鍵セットで署名を返す。参加者は「この主催者のイベントにN回来た」ことを、N枚を提示して新しいN枚と交換する形で証明できる。主催者は常連優先枠や荒らし対策に使える。

## 5. Marmot / White Noiseの使い方

Marmotは「メールなしで参加者に連絡する」手段と、会場限定チャットの土台として使う。Nostrの鍵とリレー網にMLS（RFC 9420）を重ねたグループ暗号化プロトコルで、電話番号もメールも要らず、リレー運営者には暗号文しか見えない。

### ライブラリの現状（2026年11月時点の調査）

| 実装 | 状態 | このプロジェクトでの扱い |
| --- | --- | --- |
| marmot-ts | TypeScript実装。アルファ版で、READMEに「まだ本番で使わないこと」と明記。保存先はIndexedDBなどを差し替え可能 | ブラウザ側で採用。バージョン固定 |
| MDK | Rustの参照実装。White Noiseが使う本番向けスタック | ルームエージェントの代替候補 |
| marmot-server | MDKをREST APIとして公開するDockerサービス | 同上 |
| marmots-web-chat | marmot-tsのブラウザチャット例 | 実装の手本として参照 |

プロトコルはまだ動いている。2026年3月には暗号方式をNIP-44からChaCha20-Poly1305へ変える破壊的変更があった。marmot-tsとMDKの相互運用にも未対応の組み合わせが報告されている。White Noiseアプリとの互換は、動く前提にせず実機で確かめる。

### 設計方針

- **アダプター層で隔離する。** アプリ本体は `MessagingAdapter`（ルーム作成、参加、送信、受信、退出）だけを呼ぶ。Marmotの変更は `packages/messaging` の中で吸収する。
- **重要な連絡をMarmotだけに依存させない。** 中止や会場変更はイベントページにも掲示する。チケットを持つブラウザはページを開けば常に最新のお知らせを読める。
- **参加者はイベントごとの使い捨てNostr鍵で入る。** MLSではメンバー同士に公開鍵が見えるため、普段のnpubは使わせない。

### 入室の流れ

1. ブラウザがイベント用の使い捨て鍵を作り、MLSのキーパッケージをリレーに公開する。
2. ブラウザが入室パス（roomトークン）と使い捨て公開鍵をルームエージェントに送る。
3. エージェントがパスを検証して消し込み、その鍵をグループに追加する。
4. ブラウザがWelcomeメッセージを受け取り、ルームに入る。

入室パスもブラインド署名なので、エージェントは「正規の参加者である」ことしか分からない。エージェントはメンバー追加を1件ずつ直列に処理する。

### ルームでできること

| 機能 | 内容 | フェーズ |
| --- | --- | --- |
| お知らせ | 主催者の投稿を目立たせて表示。イベントページにも同じ内容を掲示 | 3 |
| 仮面チャット | 使い捨て鍵から決まるランダムな仮面アバターと名前で会話 | 3 |
| 時限消滅 | 終了24時間後にエージェントがグループを解散し、ブラウザが端末内の履歴と鍵を削除 | 3 |
| 両想い開示 | 相手の仮面をタップすると「開示してもよい」が暗号化して送られる。双方がタップしたときだけ、各自が選んだnpubを交換 | 4 |
| 匿名投票・質問 | チェックイン済みの人に配る投票トークンで1人1票を保証 | 4 |
| White Noiseで開く | 参加者がWhite Noiseアプリ側の鍵で入室パスを使う。互換性の検証後に提供 | 4（要検証） |

両想い開示は、受け取った「開示してもよい」を画面に出さないことで成立する。改造したクライアントなら片想いを検知できるため、その限界を説明に書く。

### 時限消滅の限界

リレーには暗号文が残りうる。MLSの前方秘匿性により、鍵を削除した後は復号できない。ただし、他の参加者が画面を撮影・保存することは防げない。

## 6. 主要フロー

画面は「イベントページ」「マイチケット」「主催者ダッシュボード」「受付スキャナー」「ルーム」「御朱印帳」の6つ。参加者がチケットを手にするまでを、無料イベントなら2タップ以内に収める。

### A. イベント作成（主催者）

1. Nostr拡張（NIP-07）かリモート署名（NIP-46）でログインする。主催用の別npubでもよい。
2. タイトル、日時、場所、定員、説明、カバー画像を入力する。場所は「チケット保持者にだけ表示」を選べる。
3. 発行条件を選ぶ：誰でも（PoW付き）／招待コード／有料／承認制。選択に応じて参加者側の匿名性レベルが表示される。
4. 有料の場合、NWC接続文字列を登録する（請求書の作成と確認だけの権限でよい）。
5. 公開するとイベントURLができる。任意でNIP-52のカレンダーイベントとしてNostrにも告知する。

### B. チケット取得（参加者）

1. イベントURLを開く。ログイン画面はない。
2. 「参加する」を押す。有料ならLightning請求書のQRが出るので支払う。
3. ブラウザがチケットと入室パスを受け取り、端末内に保存する。
4. チケット画面に切り替わり、バックアップとホーム画面への追加を促す。
5. 任意でルームに入る。入らなくても参加できる。

### C. チェックイン（受付）

1. 主催者がダッシュボードで受付リンクを発行し、スタッフのスマホで開く。リンクはそのイベントの消し込み権限だけを持ち、終了後に失効する。
2. 参加者がチケットQRを見せる。
3. スキャナーが読み取り、緑（入場OK）／赤（使用済み・無効）を全画面で表示する。
4. 参加者のブラウザが消し込みを検知し、御朱印を受け取って演出を出す。
5. ダッシュボードの来場カウンターが1増える。

### D. イベント後

1. 終了24時間でルームが解散される。
2. サーバーは支払い記録とイベントの秘密鍵を削除し、集計値（発行数・来場数）だけを残す。
3. 参加者の端末には御朱印だけが残る。

## 7. データモデルとAPI

サーバーのDBには参加者を表すテーブルが存在しない。これが設計上の一番の特徴で、READMEの冒頭にも書く。

### テーブル

| テーブル | 主な列 | 保持期間 |
| --- | --- | --- |
| hosts | pubkey | 退会まで |
| events | id, host_pubkey, title, description, starts_at, ends_at, location, location_visibility, capacity, issue_policy, price_msat, issued_count, redeemed_count, status | 主催者が削除するまで |
| event_cohosts | event_id, pubkey | イベントと同じ |
| keysets | id, event_id または host_pubkey, kind (ticket / room / stamp), public_key, private_key（暗号化保存） | ticket・roomの秘密鍵は終了48時間後に削除 |
| spent | keyset_id, y（秘密値の照合値） | 鍵セットと同じ |
| quotes | id, event_id, payment_hash, state, expires_at | 終了48時間後に削除 |
| invite_codes | event_id, code_hash, uses_left | イベント終了まで |
| approvals | event_id, applicant_pubkey, state | 終了48時間後に削除（承認制のみ） |
| announcements | id, event_id, body, created_at | イベントと同じ |
| scanner_links | event_id, token_hash, expires_at | イベント終了まで |
| pending_stamps | blinded_hex, signature_hex, expires_at | 24時間 |

**保存しないもの**：IPアドレス、User-Agent、メール、氏名、チケット発行時のブラインド値、発行と支払いの対応、Cookie、アクセス解析。リバースプロキシのログも既定で無効にした設定例を同梱する。

### API

主催者向けの操作はNIP-98（Nostr署名によるHTTP認証）で守る。参加者向けは認証なし。

| メソッドとパス | 認証 | 内容 |
| --- | --- | --- |
| `GET /api/events/:id` | なし | イベント情報、公開鍵、残り枠、お知らせ |
| `POST /api/events` | 主催者 | イベント作成（鍵セットも生成） |
| `PATCH /api/events/:id` | 主催者 | 編集、公開、中止 |
| `POST /api/events/:id/quote` | なし | 有料：請求書を返す。無料：PoWの課題を返す |
| `POST /api/events/:id/issue` | なし | 条件（支払い済みquote、PoW解、招待コード）とブラインド値を受け、署名とDLEQを返す |
| `POST /api/events/:id/redeem` | 受付リンク | チケットを検証して消し込む。スタンプ用ブラインド値があれば署名して保管 |
| `POST /api/events/:id/return` | なし | チケット返却（枠を戻す） |
| `GET /api/stamps/:blinded` | なし | チェックイン後のスタンプ署名を受け取る |
| `POST /api/stamps/swap` | なし | スタンプN枚を新しいN枚と交換（参加実績の証明） |
| `POST /api/events/:id/room/join` | なし | 入室パスと使い捨て公開鍵を受け、グループに追加 |
| `POST /api/events/:id/announcements` | 主催者 | お知らせ投稿（ページとルームの両方に出す） |
| `POST /api/events/:id/scanner-links` | 主催者 | 受付リンクの発行・失効 |
| `GET /api/events/:id/stats` | 主催者 | 発行数、来場数、時刻別の来場推移（15分単位） |

無料イベントの乱用対策はIP制限ではなくPoWと招待コードで行う。IPベースの制限はTor利用者を締め出し、IPの記録も必要になるため採用しない。

## 8. 実装フェーズ

5つのフェーズに分け、フェーズ1の終わりに実際の小規模イベントで試せる状態にする。不安定なMarmotはフェーズ3に置き、それまでにチケットの中核を固める。

| フェーズ | 作るもの | 完了条件 |
| --- | --- | --- |
| 0. 土台 | モノレポ、packages/core（BDHKE、DLEQ、トークンの符号化）、CI | CashuのNUT-00 / NUT-12テストベクターがすべて通る |
| 1. MVP（無料イベント） | イベント作成、イベントページ、PoW付き発行、マイチケット、受付スキャナー、カウンター、お知らせ掲示、Docker Compose | スマホ2台で作成→取得→入場→二重入場の拒否まで通る。PlaywrightのE2Eが通る |
| 2. 運営機能 | NWCによる有料チケット、招待コード、共同主催者、オフライン受付、チケット返却、バックアップ、日英切替 | テスト用ウォレットで支払い→発行が通る。機内モードで受付できる |
| 3. ルーム | packages/messaging（MessagingAdapter + marmot-ts実装）、ルームエージェント、入室パス、仮面チャット、時限消滅 | ブラウザ3つで入室→会話→解散が通る |
| 4. 遊びと発展 | 御朱印帳、両想い開示、匿名投票、抽選、デポジット（hold invoice）、承認制、White Noise連携の検証 | 機能ごとに判断 |

各フェーズの終わりに `docs/PRIVACY.md`（サーバーが見るもの・保存するものの一覧）を更新する。この文書がプロジェクトの信用の根拠になる。

## 10. 未解決事項とリスク

公開前に決めることが5つ、検証が必要な技術的前提が4つある。

### 決めること

- [ ] 正式名称とドメイン（「Kamen」は仮称）
- [ ] ライセンス：MITかAGPLv3か
- [ ] 公式インスタンスを運営するか、セルフホスト専用にするか。運営する場合の費用負担
- [ ] 最初に試すイベントと、そのときの併用方法（告知は既存サービス、チケットだけこちら、など）
- [ ] 違法・迷惑なイベントが作られた場合の対応方針（主催者はnpubで識別できるが、参加者は識別できない）

### 検証が必要な技術的前提

| 前提 | リスク | 確かめ方 |
| --- | --- | --- |
| marmot-tsがブラウザとNode.jsの両方で安定して動く | アルファ版で破壊的変更が起きる | フェーズ3の最初に調査と小さな試作を行う。だめならMDKベースに切り替える |
| White Noiseアプリから同じルームに入れる | 実装間の互換が取れていない組み合わせがある | 実機で試す。動くまで機能として謳わない |
| hold invoiceを数日間保持できる | 保持期間に上限があり、経路上の資金も拘束する | Alby Hubなどで実際の上限を測る。短ければ「前日から受付」にする |
| 主催者のウォレットがNWCに対応している | 非対応ウォレットの主催者は有料イベントを作れない | 対応ウォレットの一覧を案内する。将来LNURL・BOLT12も検討 |

### 法務（専門家に確認すること）

- チケットトークンは金銭価値を持たせず、資金も預からない設計にしている。それでも、有料チケットの販売やデポジットが日本の資金決済法などにどう扱われるかは確認が要る。
- ドリンク券や抽選の賞金のように価値を持つトークンを扱う機能は、確認が済むまで実装しない。
- 会場や保険の都合で参加者名簿が求められるイベントには使えない。主催者向けの説明に明記する。
